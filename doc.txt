1. Visão Geral
1.1 Objetivo
Construir um núcleo bancário (contas, depósitos, saques, transferências) em que o
estado nunca é sobrescrito: toda mudança é gravada como um evento imutável em um
log append-only (Event Sourcing). Leituras são servidas por modelos de leitura separados
(CQRS), alimentados pelos eventos.
1.2 Por que Event Sourcing em banco
Necessidade bancária Como o padrão atende
Auditoria e conformidade (BACEN, SOX,
LGPD)
O histórico completo é o próprio
armazenamento, não um log auxiliar.
Rastreabilidade de saldo Saldo = soma dos eventos. Qualquer saldo
pode ser reconstruído e explicado.
Investigação de fraude e disputas Time travel: reconstruir o estado de uma conta
em qualquer instante.
Novos relatórios no futuro Basta criar uma nova projeção e reprocessar o
histórico.
Alta concorrência de escrita Inserções append-only, sem UPDATE  e sem
contenção em linhas de saldo.

1.3 CRUD x Event Sourcing
1.4 Quando NÃO usar
Evite ES em CRUDs simples, sem requisito de histórico, ou se a equipe não tem disposição
para lidar com consistência eventual e evolução de eventos. Aplique apenas nos
agregados em que o histórico agrega valor (Conta, Transferência); cadastros auxiliares
podem continuar CRUD.
2. Escopo
Dentro do escopo: abertura e encerramento de conta, depósito, saque,
bloqueio/desbloqueio, transferência entre contas (via Saga), extrato e saldo (read
models), snapshots, projeções reconstruíveis, idempotência, versionamento de eventos,
observabilidade, proteção de dados pessoais.
Fora do escopo: autenticação real, integração com PIX/SPB/cartões, KYC, câmbio, multi-
região.

4.4 Fluxo de um comando (depósito)
1. API recebe POST /contas/{id}/depositos  com Idempotency-Key .
2. Handler verifica a chave de idempotência.
3. Carrega o stream: último snapshot + eventos posteriores.
4. Reidrata o agregado Conta  aplicando os eventos.
5. Executa conta.depositar(valor) , que valida e retorna ValorDepositado .
6. Event Store faz append  com expectedVersion . Se outro comando gravou antes,
ocorre ConcurrencyException  (retry ou 409).
7. Responde 202/201  ao cliente.
8. Publisher entrega o evento ao Kafka; projetores atualizam os read models.
Conceito Definição no projeto
Projection / Read Model Visão derivada dos eventos, otimizada para
consulta.
Saga / Process Manager Coordena fluxo entre agregados (transferência).

5.3 Concorrência otimista
A constraint UNIQUE (stream_id, version)  é a garantia final. O append é feito com a
versão esperada; se outra transação já gravou aquela versão, o banco rejeita e a aplicação
lança ConcurrencyException .
public void append(String streamId, int expectedVersion, List<DomainEvent> 
events,
                   EventMetadata meta) {
    try {
        int version = expectedVersion;
        for (DomainEvent e : events) {
            version++;
            jdbc.update(INSERT_SQL, e.eventId(), streamId, "Conta", version,
                        e.getClass().getSimpleName(), e.schemaVersion(),
                        serializer.toJson(e), serializer.toJson(meta));
        }
    } catch (DuplicateKeyException ex) {
        throw new ConcurrencyException(streamId, expectedVersion);
    }
}
O append  roda em uma única transação: ou todos os eventos do comando entram, ou
nenhum.
5.4 Cuidado com a ordem global

transação pode obter a posição 10, outra a 11, e a 11 fazer commit antes. Um projetor que lê
até 11 e salva o checkpoint pode pular o evento 10. Soluções:

public class Conta {
    private UUID id;
    private BigDecimal saldo = BigDecimal.ZERO;
    private BigDecimal limite = BigDecimal.ZERO;
    private Status status = Status.NOVA;
    private int versao = 0;                      // versão do stream
    private final List<ContaEvent> pendentes = new ArrayList<>();
    enum Status { NOVA, ATIVA, BLOQUEADA, ENCERRADA }
    // ---------- Decisão (comandos) ----------
    public static Conta abrir(UUID id, String titularRef, BigDecimal limite, 
Clock clock) {
        Conta c = new Conta();
        c.registrar(new ContaAberta(UUID.randomUUID(), id, titularRef, 
limite, clock.instant()));
        return c;
    }
    public void depositar(BigDecimal valor, String origem, Clock clock) {
        garantirOperavel();
        exigirPositivo(valor);
        registrar(new ValorDepositado(UUID.randomUUID(), id, valor, origem, 
clock.instant()));
    }
    public void sacar(BigDecimal valor, Clock clock) {
        garantirOperavel();
        if (status == Status.BLOQUEADA) throw new 
ContaBloqueadaException(id);
        exigirPositivo(valor);
        if (saldo.add(limite).compareTo(valor) < 0) throw new 
SaldoInsuficienteException(id);
        registrar(new ValorSacado(UUID.randomUUID(), id, valor, 
clock.instant()));
    }
    public void encerrar(Clock clock) {
        garantirOperavel();
        if (saldo.signum() != 0) throw new SaldoNaoZeradoException(id);
        registrar(new ContaEncerrada(UUID.randomUUID(), id, 
clock.instant()));
    }
    // ---------- Mutação (apenas aplica fatos, sem validação) ----------

    private void aplicar(ContaEvent e) {
        switch (e) {
            case ContaAberta ev      -> { id = ev.contaId(); limite = 
ev.limite(); status = Status.ATIVA; }
            case ValorDepositado ev  -> saldo = saldo.add(ev.valor());
            case ValorSacado ev      -> saldo = saldo.subtract(ev.valor());
            case ContaBloqueada ev   -> status = Status.BLOQUEADA;
            case ContaDesbloqueada ev-> status = Status.ATIVA;
            case ContaEncerrada ev   -> status = Status.ENCERRADA;
        }
        versao++;
    }
    private void registrar(ContaEvent e) { aplicar(e); pendentes.add(e); }
    public static Conta reconstruir(List<ContaEvent> historico) {
        Conta c = new Conta();
        historico.forEach(c::aplicar);   // não adiciona em 'pendentes'
        return c;
    }
    private void garantirOperavel() {
        if (status == Status.NOVA || status == Status.ENCERRADA) throw new 
ContaInvalidaException(id);
    }
    private void exigirPositivo(BigDecimal v) {
        if (v == null || v.signum() <= 0) throw new 
ValorInvalidoException(v);
    }
    public List<ContaEvent> eventosPendentes() { return 
List.copyOf(pendentes); }
    public int versaoPersistida() { return versao - pendentes.size(); }
}
6.3 Regras de ouro do domínio
1. O método aplicar  nunca valida nem lança exceção: o evento já aconteceu.
2. O método aplicar  é determinístico: sem Instant.now() , UUID.randomUUID() , I/O
ou chamadas externas. O tempo e os ids entram na decisão (via Clock ) e ficam
gravados no evento.
3. Um comando afeta um único agregado por transação.
4. Eventos são record s imutáveis, nomeados no passado.

7. Lado de Comando (Application)
7.1 Command Handler
@Service
public class DepositarHandler {
    private final EventStore store;
    private final Clock clock;
    private final IdempotencyService idempotency;
    @Transactional
    public void handle(DepositarValor cmd) {
        if (idempotency.jaProcessado(cmd.idempotencyKey())) return;
        var stream = store.load("conta-" + cmd.contaId());     // snapshot + 
eventos
        Conta conta = Conta.reconstruir(stream.events());
        conta.depositar(cmd.valor(), cmd.origem(), clock);
        store.append(stream.id(), stream.version(), conta.eventosPendentes(),
                     EventMetadata.of(cmd.correlationId(), cmd.userId()));
        idempotency.registrar(cmd.idempotencyKey());
    }
}
7.2 Estratégia de retry em conflito
Em ConcurrencyException , o handler recarrega e reexecuta o comando (até 3
tentativas, com jitter curto). Se persistir, a API devolve 409 Conflict . Como a decisão é
refeita sobre o estado novo, a regra de saldo é sempre reavaliada.
7.3 Snapshots
Gerar snapshot a cada N = 100 eventos (ajustar com métricas).
Snapshot é otimização descartável: o sistema deve funcionar corretamente sem ele.
Grave a versão do esquema do snapshot; se mudar a classe, descarte e recrie a partir
dos eventos.

7.4 Transferência entre contas (Saga)
Como um comando altera apenas um agregado, a transferência é uma Saga (process
manager), não uma transação única:
TransferenciaSolicitada
   → [Saga] comando SacarParaTransferencia (conta origem)
        ├ ─ ValorSacado → [Saga] comando DepositarTransferencia (conta 
destino)
        │      ├ ─ ValorDepositado → TransferenciaConcluida
        │      └─ falha (conta encerrada/bloqueada) → [Compensação] Estornar 
na origem
        │                                              → 
TransferenciaEstornada
        └─ SaldoInsuficiente → TransferenciaRejeitada
O estado da saga também pode ser event sourced ( transfer-{uuid} ).
Cada passo é idempotente e carrega transferId  como correlationId .
Compensações são novos eventos ( ValorEstornado ), nunca remoção de eventos.
Prazo máximo (timeout) por etapa, com tratamento de saga travada.

Regras de projeção:
Projetor e checkpoint são atualizados na mesma transação.
Projetores são idempotentes (reprocessar o mesmo evento não altera o resultado).
Projetores não chamam comandos nem geram eventos de negócio.
Reconstrução: truncar o read model, zerar o checkpoint e reprocessar tudo
(preferencialmente em blue/green: construir tabela nova e trocar).

9. Publicação de Eventos (integração)
O Event Store já é durável, então ele funciona como o próprio outbox: um Event Publisher
lê eventos a partir de um checkpoint e publica no Kafka (at-least-once).
Chave da mensagem = streamId  (preserva ordem por conta na partição).
eventId  como messageId ; consumidores deduplicam (Inbox).
Publique eventos de integração (contrato estável e enxuto), não exponha diretamente
o formato interno dos eventos de domínio para outros contextos.
Esquemas versionados em Schema Registry (Avro/JSON Schema) com
compatibilidade retroativa.

Implementação da fase 7: o publisher lê o Event Store em lotes, usa a chave
streamId no Kafka e registra o envelope JSON Schema v1 no subject
<topico>-value. O valor usa o wire format Confluent (magic byte + schema ID +
JSON). O checkpoint é atualizado na mesma transação PostgreSQL somente depois
dos acknowledgements do Kafka; uma falha pode causar reenvio, portanto a
entrega é at-least-once e consumidores devem deduplicar por eventId.

Para habilitar o publisher na API, configure banco.messaging.enabled=true,
banco.messaging.bootstrap-servers (padrão localhost:9092) e
banco.messaging.schema-registry-url (padrão http://localhost:8081). Credenciais
opcionais: banco.messaging.schema-registry-username/password. O Registry deve
usar compatibilidade BACKWARD para os subjects publicados. O intervalo de
polling (1000 ms) e o lote (100 eventos) podem ser ajustados com
banco.messaging.poll-interval e banco.messaging.batch-size. Desabilitado por
padrão para manter a API utilizável sem Kafka/Schema Registry.

10. Evolução de Eventos (Upcasting)
Eventos gravados jamais são editados. Quando o formato muda:
public class ValorDepositadoV1ToV2 implements Upcaster {
    public boolean supports(String type, int schemaVersion) {
        return type.equals("ValorDepositado") && schemaVersion == 1;
    }
    public JsonNode upcast(JsonNode v1) {
        ObjectNode v2 = v1.deepCopy();
        v2.put("origem", "DESCONHECIDA");   // campo novo em V2
        return v2;
    }
}
Regras: nunca remover campos usados por versões antigas; manter testes com um corpus
de eventos reais de cada versão; versionar sempre ( schema_version ).

11. Segurança, LGPD e Auditoria
11.1 Dados pessoais em log imutável
O direito de exclusão (LGPD/GDPR) conflita com um log imutável. Estratégias, em ordem
de preferência:
1. Não colocar dados pessoais nos eventos. Use referências ( titularRef ) e mantenha
o cadastro em tabela mutável separada.
2. Crypto-shredding: quando for inevitável, criptografe os campos pessoais com uma
chave exclusiva por titular (AES-GCM, chaves em KMS/Vault). Para "apagar", descarte
a chave; os eventos permanecem, mas ilegíveis.
3. Registros que a lei obriga a manter (ex.: transações financeiras) têm base legal de
retenção; documente a decisão com o jurídico/DPO.
11.2 Demais controles
TLS no banco, broker e APIs; segredos em cofre.
Usuário da aplicação com apenas INSERT / SELECT  em events .
Metadados de auditoria ( userId , correlationId , IP/origem) em todo evento.
Cadeia de integridade opcional: cada evento guarda o hash do anterior (hash chain)
para detectar adulteração.
Backups cifrados e teste periódico de restauração.

Quando 20 saques de 100,00 são enviados simultaneamente

Dado um depósito processado com a Idempotency-Key K
Quando o mesmo comando é reenviado com a chave K
Então nenhum novo evento é gravado
E a resposta é equivalente à primeira
CA-06 Reconstrução determinística
Dado qualquer stream
Quando reconstruo o agregado duas vezes a partir dos mesmos eventos
Então o estado é idêntico
E com ou sem snapshot o resultado é o mesmo
CA-07 Time travel
Dado uma conta com eventos ao longo de 30 dias
Quando consulto o saldo na data D
Então recebo a soma apenas dos eventos com occurredAt <= D
CA-08 Reconstrução de projeção
Quando eu apago rm_extrato e reprocesso desde a posição 0
Então o conteúdo final é idêntico ao anterior
CA-09 Projetor idempotente
Quando o mesmo evento é entregue duas vezes ao projetor
Então o extrato não tem linha duplicada e o saldo não é somado duas vezes
CA-10 Transferência com sucesso
Dado contas A (200,00) e B (0,00)
Quando transfiro 80,00 de A para B
Então A = 120,00 e B = 80,00 ao final da saga
E o total do sistema permanece constante
CA-11 Transferência com compensação
Dado que a conta destino está encerrada
Quando transfiro 80,00 de A para ela
Então a saga estorna 80,00 em A com um evento compensatório
E o saldo final de A é o original
E o histórico mantém saque e estorno visíveis

13. Boas Práticas e Anti-padrões
13.1 Modelagem de eventos
Nomeie no passado e no vocabulário do negócio: ValorDepositado , não
ContaAtualizada .
Evite eventos "CRUD" genéricos ( ContaAlterada ); o motivo da mudança faz parte do
valor do padrão.
Eventos pequenos e focados; inclua dados suficientes para as projeções sem consultar
outros sistemas.
Faça o Event Storming com o negócio antes de codificar para descobrir eventos e
agregados.
13.2 Agregados
Mantenha-os pequenos. Um agregado por fronteira de consistência real.
Streams com milhões de eventos são sinal de agregado mal delimitado. Exemplo: para
contas muito movimentadas, considere fechar o período (evento PeriodoFechado
com saldo inicial) e iniciar um novo stream.
Referência entre agregados apenas por id.
13.3 Leitura e escrita
Nunca consulte read models dentro do command handler para decidir regra.

Cada projeção atende uma necessidade de consulta; crie mais projeções em vez de

Projete as APIs de comando como task-based ( /depositos , /saques ), não PUT

13.4 Operação
Propague correlationId  do HTTP até o consumidor (OpenTelemetry).
Ferramentas de suporte: consulta de stream por conta, replay controlado e
reconstrução de projeção.
13.5 Anti-padrões
Usar o Event Store como fila genérica ou como banco para consultas.
Editar ou apagar eventos "só dessa vez" (corrija com evento compensatório).
Lógica de negócio, now()  ou chamadas externas dentro do aplicar .
Compartilhar eventos de domínio internos como contrato público entre serviços.
Um único projetor monolítico que não pode ser reconstruído.
Ignorar versionamento de eventos até o primeiro problema em produção.
Adotar Event Sourcing no sistema inteiro por padrão.

17. Decisões Arquiteturais (ADRs resumidos)
18. Glossário
Event Sourcing: persistir mudanças como sequência imutável de eventos; o estado é
derivado por replay.
CQRS: separação entre modelo de escrita (comandos) e modelo de leitura (consultas).
Stream: sequência ordenada de eventos de um agregado.
Snapshot: estado consolidado em uma versão, para evitar replay completo.
Projection / Read Model: visão derivada dos eventos, otimizada para leitura.

20. Operação das fases 8 e 9

20.1 Chave de dados pessoais
O serviço exige BANCO_CRYPTO_MASTER_KEY: chave AES-256 codificada em Base64,
fornecida por um gerenciador de segredos fora do repositório. Não use uma chave
de exemplo em produção. A ausência ou formato incorreto da chave impede a
inicialização; perder a chave mestra torna ilegíveis as chaves de conta
armazenadas. Planeje backup seguro e rotação por re-envelopamento antes da
implantação.

Eventos ContaAberta gravados após a ativação do recurso cifram titularRef com
AES-GCM e uma chave por conta. Destruir essa chave impede a recuperação dos
valores cifrados sem apagar os eventos financeiros. O histórico anterior à
migração permanece em texto claro e não é protegido retroativamente; por isso,
CA-13 não está integralmente satisfeito para dados legados até que exista um
processo aprovado de migração. Backups e cópias anteriores também precisam ser
considerados no procedimento de retenção. Snapshots não armazenam titularRef.

20.2 Verificação da cadeia
JdbcEventIntegrityVerifier verifica a sequência de hashes por stream em uma
transação repeatable-read e retorna a quantidade verificada e a primeira posição
inválida. As posições anteriores à V5 são tratadas como limite de confiança:
a migração cria o início da cadeia após o último evento existente. A cadeia
detecta alterações e omissões em eventos protegidos, mas não é uma assinatura
externa e não impede um administrador de banco de reescrever toda a cadeia.
Execute a verificação por ferramenta administrativa protegida; ela não é
exposta como endpoint HTTP público.

20.3 Observabilidade e validação
O endpoint de health e os endpoints metrics/prometheus do Actuator permitem
verificar saúde, timers de lote, eventos processados, lotes com falha e lag de
projeção/publicador quando esses componentes executam. Configure
OTEL_EXPORTER_OTLP_ENDPOINT para um coletor OpenTelemetry; o sampling padrão é
10% e pode ser alterado por TRACING_SAMPLING_PROBABILITY. X-Correlation-Id é
gerado quando ausente, validado como UUID, devolvido na resposta, incluído nos
logs JSON, metadados de eventos e observação distribuída. Restrinja os endpoints
de métricas e health pela rede/ingress; não os publique sem controles de acesso.

Validação local sem banco/container: mvn -pl infrastructure -am test e
mvn -pl api-command -am test. Os testes *IT que validam PostgreSQL, migrations,
carga concorrente, imutabilidade e falha do publisher requerem Docker e devem
ser executados com mvn -pl infrastructure -am verify e
mvn -pl api-command -am verify. As metas de latência, throughput e lag devem
ser medidas em ambiente representativo; os testes de resiliência existentes
não constituem evidência de que RNF-03 a RNF-06 foram atingidos.
